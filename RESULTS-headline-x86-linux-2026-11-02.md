# Headline rows on one x86-64 box: Vif, Rust, Go, Bun, Zig (2026-11-02)

This run measures the benchmarks page's five headline rows (HTTP, pipelined HTTP, memory, JSON, N-body)
on one machine with one method, so every bar can come from the same run. Vif, Rust, Go, Bun and Zig
take part in the same interleaved rounds. It is a measurement only: the axon checkout was used as-is
and nothing was tuned.

**Vif is ahead of every competitor on every row.** The closest cell is dynamic JSON against Bun: 1.09×
faster at the median, and faster in all 15 paired rounds, but the overall ranges overlap slightly (Vif
185.0–201.0 ms, Bun 199.2–253.4 ms). Every other cell has separate ranges.

## Method

### HTTP (hello, pipelined, memory)

This is the r3 4-vCPU method (`RESULTS-zig-vs-vif-linux-2026-11-02-r3.md`), run by
`bench/headline/run_headline.py http`.

- **Placement:**
  - Every server runs under `taskset -c 0`, including all of its threads, and its SMT sibling CPU 1 stays idle.
  - `wrk -t2 -c64 --latency --timeout 5s` and the Python driver and samplers run on CPUs 2–3, the other physical core.
- **Rounds:**
  - Each run starts a fresh server, gives it a 2 s warm-up and then measures 10 s.
  - 11 rounds per scenario. The server order alternates every round.
- **Validation:**
  - Before the load runs, each server must answer `GET /` with 200 and `Hello, World!` and a correct Content-Length.
  - It must also answer 16 GETs written on one socket with 16 such responses.
  - No measured run had socket errors or non-2xx responses.
- **Vif:**
  - Runs with `AXON_THREADS=1` and the default io_uring backend.
  - Validation confirmed that one io_uring instance was open in the server.
- **http.zig "default" and "1+1":**
  - "Default" is its stock configuration: 1 worker and a 32-thread handler pool.
  - "1+1" is `HTTPZ_WORKERS=1 HTTPZ_POOL=1`.
  - Both answer only the first request of a pipelined write. They pass the hello check and fail the 16-deep check, so the pipelined row has no http.zig entry.
- **Pipelined load:** `bench/http/pipeline.lua` writes 16 requests per send.
- **Server CPU:** user + system time of the server's whole process tree, from `/proc/PID/stat`.
- **Memory** (the metric of the ARM field report, `bench/http/compare.py`):
  - Peak aggregate PSS: the sum of `Pss:` from `/proc/PID/smaps_rollup` over the server's live process tree.
  - Sampled every 100 ms during the measured 10 s of each hello run, after the warm-up.
  - Peak aggregate Rss is recorded alongside. Every server here is a single process.

**Every server was server-bound in both scenarios.** Every server kept its CPU 1.00 busy, while wrk used
at most 1.37 of its two CPUs. Throughput therefore tracks server CPU per request.

wrk's pipelined latency histogram is not meaningful: for Vif it printed a p99 of 0.00 µs. The pipelined
row is therefore throughput only.

### JSON and N-body

Run by `bench/headline/run_headline.py cli`.

- **Timing:** complete-process wall time, including launch, allocation, the work, output and exit.
- **Pinning:**
  - Every process is pinned with `taskset -c 0`, with `AXON_THREADS`, `GOMAXPROCS`, `RAYON_NUM_THREADS`, `ZIG_THREADS` and `TOKIO_WORKER_THREADS` all set to 1.
  - Go's N-body workers follow `runtime.NumCPU()`, which honours the affinity mask, so it runs one worker.
- **Rounds:** 2 warm-up rounds, then 15 measured rounds. Each round runs every variant once, in a shuffled order (seed 20261102).
- **JSON:** the field report's "construct varying JSON, fully parse it, read integer/UTF-8/array fields, checksum and release" workflow, with 1,000,000 documents. The variants:
  - Vif: `examples/library_bench.ax`, mode 0.
  - Rust: `bench/rust` `usability parse`.
  - Go: `bench/core/json.go`.
  - Bun: `bench/usability/bun.ts parse`.
  - Zig: `bench/zig/json.zig`, five variants, so that the dynamic `Value` and the fastest typed/arena variant can both be reported.
- **N-body:**
  - Vif: `examples/nbody.ax`.
  - Rust: `bench/rust` `nbody`, using rayon with one thread.
  - Go: `bench/go/nbody`.
  - Bun: `bench/core/compute.ts nbody`.
  - Zig: `bench/zig/nbody.zig`, baseline and native builds.
- **Output checks:**
  - Every JSON run printed the independent checksum 513500000.
  - Every N-body energy agreed with the first within a relative 1e-9 (−0.89384892881525…).
  - There were no mismatches.

Vif against Bun on JSON, round by round:

- Vif was faster in all 15 paired rounds.
- Vif's two slowest runs (200.4 and 201.0 ms) reach into Bun's two fastest (199.2 and 200.8 ms).
- The quartiles are 186.2 / 187.1 / 190.3 ms for Vif and 201.8 / 204.5 / 212.4 ms for Bun.

CLI peak RSS is recorded per run with GNU time's `%M`, but it is not a headline metric. Linux carries the
pre-exec high-water mark across `exec`, so values near 1.9 MiB are a floor, not a measurement.

## Notes for the site

- **Rows where this x86 run differs from the ARM field report.** Absolute numbers change because the
  machine and the HTTP client protocol differ. Some orderings change as well:
  - N-body: Go was the fastest single-worker N-body on the ARM VM (296 ms against Axon's 817 ms). Here it is the slowest (1,190 ms against Vif's 376 ms).
  - N-body: Rust tied Axon there; here it is 1.82× behind.
  - The JSON and HTTP orderings match the field report.
- **Pipelined row.** There is no http.zig entry, because it does not answer pipelined requests. The fastest Zig server that does is std.http.
- **Memory row.** This is peak aggregate PSS, as in the field report. Vif's 0.79 MiB is all private: Vif is a static binary with no shared libraries, so its PSS equals its RSS. Rust's PSS (1.91 MiB) is below its RSS (3.88 MiB) because libc pages are shared.
